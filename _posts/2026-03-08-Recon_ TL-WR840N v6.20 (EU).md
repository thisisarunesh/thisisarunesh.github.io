## Introduction

Consumer routers might look like ordinary plastic boxes, but to anyone who loves digging into hardware, they’re endlessly fascinating. They’re cheap, everywhere, and usually run stripped-down versions of Linux—often going years without a single update. That’s exactly what makes them such a playground for anyone interested in embedded security, firmware reverse engineering, or hardware hacking.

The real fun starts at the boot sequence. By connecting to the UART console, you can watch the router come to life, step by step, revealing the bootloader, kernel startup, and other low-level systems that are usually hidden from view. It’s like lifting the hood on a device billions of people rely on every day, giving you a peek at the hidden machinery that keeps it running.

## Locating the UART Header

Like most embedded networking devices, the router’s motherboard exposes a 4-pin UART debugging header used during manufacturing and development.

![](/assets/images/posts/2.jpg)

Typical UART pin layout on the board:

| Pin  | Function                                                     |
| ---- | ------------------------------------------------------------ |
| VCC  | Power supply                                                 |
| GND  | Shared ground reference, ensuring a common voltage reference between devices |
| RX   | Receives data                                                |
| TX   | Transmit data                                                |

## Hardware Setup

To connect to the router’s UART, a `FTDI FT232R USB-to-TTL Serial Converter` was used. Before powering anything up, it’s important to verify the voltage. A quick multimeter check showed about 3.3V between the router’s TX pin and the GND pin, which matches the converter’s 3.3V setting. The converter has a voltage selection switch, allowing it to be set to either 3.3V or 5V, so confirming the correct setting beforehand is a simple precaution that keeps the setup safe.

![](/assets/images/posts/3.jpg)

The connections between the router and converter UART pins were made as follows:

| Router | Converter | Function                                                     |
| ------ | --------- | ------------------------------------------------------------ |
| GND    | GND       | Shared ground reference, ensuring a common voltage reference between devices |
| RX     | TX        | Data transmitted by the converter is received by the router  |
| TX     | RX        | Data transmitted by the router is received by the converter  |

Note: The VCC pins on both the converter and the router were left unconnected, since the router is powered independently through its own power supply.

## Bootloader Initialization

Immediately after power-on, the bootloader began outputting debug information through the UART console. 


From this information, we can confirm:

* **Bootloader**: U-Boot 1.1.3 (Ralink-specific build 4.3.0.0)
* **CPU / SoC**: MediaTek MT7628 (MIPS-based)
* **CPU Frequency**: 580 MHz
* **RAM**: 32 MB DDR (16-bit width, 16-bit bus)
* **Flash**: SPI Flash (Manufacturer ID: `1c`, Device ID: `70 16`)
* **Caches**:
  1. **Instruction Cache**: 512 sets, 4 ways, 32-byte line size, total 64 KB
  2. **Data Cache**: 256 sets, 4 ways, 32-byte line size, total 32 KB
* **Board / SoC details**: Ralink APSoC, ASIC 7628_MP
* **Boot process info**: PHY reset performed (`RESET MT7628 PHY`), switch PHY port disabled, system continues to start normally
* **Warnings**: “Un-recognized chip ID,” suggesting the bootloader may be slightly outdated for this board

On most embedded devices, the bootloader can be caught by pressing a key (often `Esc`, `Space`, or `Enter`) during the early boot countdown. This allows you to pause startup, tweak boot parameters, or flash custom firmware. On this router, however, no prompt appeared, and pressing keys during boot had no effect. It’s likely that the firmware either disables interactive access, hides the prompt, or enforces a secure boot sequence that prevents manual intervention.

* **Bootloader access is disabled**: The firmware may skip interactive boot entirely, preventing manual intervention.  
* **Hidden or delayed prompt**: Some routers only enable bootloader interaction under very specific timing windows or hardware conditions.  
* **Secure boot mechanisms**: Certain devices lock the bootloader to prevent unauthorized firmware modifications, possibly verifying signatures before allowing access.

## Network Service Initialization

As the system continued booting, the router brought up its internal services and web-based admin interfaces. A number of local domains were registered to facilitate access to the admin panel:

```
add domain: tplinkwifi.net
add domain: tplinkap.net
add domain: tplinkrepeater.net
add domain: tplinklogin.net
tp_domain init ok
```

These domains serve as hardcoded entry points to the router’s configuration interface, letting devices on the local network reach the admin panel without relying on external DNS.
